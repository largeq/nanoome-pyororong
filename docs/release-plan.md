# 표로롱 — 네이버 카페·블로그 표 변환 배포 준비 계획

한글 for Mac에서 복사한 표를 네이버 카페에 붙여넣을 때 글자와 표 구조를 보존하고, Windows에서 한글 표를 붙여넣었을 때의 결과에 최대한 가깝게 만드는 것을 목표로 한다. 원본 글꼴을 우선 유지한다. 아래의 목표는 앞으로 구현하고 확인할 사항이며, 현재 앱이 모두 지원한다는 뜻은 아니다.

갱신일: 2026년 10월 29일. **2.0.0(빌드 1)의 [첫 GitHub Release](https://github.com/largeq/nanoome-pyororong/releases/tag/v2.0.0)와 운영 업데이트 안내 파일 게시를 완료**했다. 배포용 Universal 앱의 Developer ID 서명·Apple 공증·티켓 스테이플·Gatekeeper 검증을 마쳤다. 문서 전체·여러 표·중첩 표 변환을 구현했고, 실제 한글·네이버 붙여넣기는 사용자가 완료한 것으로 확인했다. 마지막 절에 최신 결과를 기록하며, 앞선 날짜의 검사 기록은 당시 상태로 보존한다. 작업 전 상태는 아래의 로컬 Git 백업에 보존되어 있다.

## 확인된 사용자 환경과 요구

- 한글 for Mac: **12.30.0(6544)**.
- 네이버 카페 글쓰기 브라우저: **Safari와 Chrome 모두**.
- 글꼴: 나눔고딕으로 일괄 변경하는 현재 방식에서 **원본 글꼴을 우선 유지하는 방식**으로 개선한다.
- 비교 기준: Windows에서 한글 표를 네이버 카페에 붙여넣었을 때의 결과. Windows와 한글의 버전, 실제 비교 표와 결과는 실사용 검증 단계에서 확보한다.
- 글자 크기와 테두리: 현재의 15 크기·검은 실선 처리를 최종 규칙으로 확정하지 않는다. 원본 및 Windows의 붙여넣기 결과를 비교해 보존 범위를 정한다.
- Safari·Chrome의 정확한 버전과 macOS 버전은 실사용 검증 때 기록한다.

## 첫 배포의 범위

### 우선 지원할 작업

1. 사용자가 한글에서 표 하나 또는 표가 들어 있는 문서 전체를 선택해 복사한다.
2. 메뉴바에서 표 변환을 실행한다.
3. Safari 또는 Chrome의 네이버 카페 글쓰기 화면에 붙여넣는다.
4. 글자, 셀 병합, 셀 안 줄바꿈, 정렬, 색상, 강조와 열 너비를 확인한다.
5. 원본 글꼴 정보가 붙여넣기와 저장 후에도 유지되는지 확인한다.

글자 누락과 중복 방지를 가장 먼저 해결한다. 가로·세로 셀 병합, 문단, 줄바꿈, 공백과 특수문자를 확인하고, 열 너비는 원본의 비율을 반영하도록 개선한다. 실패한 변환에서는 복사해 둔 원본 내용을 보호한다.

### 제한이 필요한 입력

처음에는 여러 표·중첩 표를 제한하는 안을 검토했으나, 사용자의 문서 전체 변환 요청과 Windows 기준 게시글에 따라 지원 범위를 확대했다. 모든 바깥 표와 본문을 순서대로 처리하고, 중첩 표는 바깥 표의 행으로 펼친다. 지나치게 복잡한 중첩·병합 구조는 원본 클립보드를 보존하며 변환을 중단한다.

본문과 링크는 처리하되, 한글 로컬 그림·수식·문서 전체의 페이지 배치까지 보존하는 기능은 아직 지원하지 않는다. 로컬·데이터 형식 그림은 별도로 추가해야 할 개수를 안내한다. 대각선은 제거 사실을 안내한다. 이 요소들의 Windows 동작은 별도의 비교 자료가 필요하다.

### 원본 글꼴 보존의 확인 기준

저장된 한글 클립보드 예시에는 `함초롬바탕`, `나눔바른고딕` 같은 원본 글꼴 이름과 글자 크기가 들어 있다. 초기 코드는 나눔고딕·15 크기로 고정했지만, 현재 코드는 원본 정보를 읽어 전달한다. 실제 네이버 화면에서의 지원 여부는 아래 기준으로 별도로 검사한다.

- 글자 자체에 지정된 글꼴뿐 아니라 상위 문단과 셀에서 물려받는 글꼴도 확인한다.
- 한 셀 안의 서로 다른 글꼴과 한글·영문이 섞인 내용을 확인한다.
- 고정된 나눔고딕 지정이 원본 글꼴을 덮어쓰지 않도록 한다.
- 변환 결과에 글꼴 이름이 들어가는 것과 실제 네이버 화면에 같은 글꼴로 보이는 것을 구분해 검사한다.
- Safari와 Chrome 각각에서 붙여넣기 직후와 저장 후 결과를 확인한다.

브라우저는 사용할 수 없는 글꼴을 다른 글꼴로 대체할 수 있다. 글꼴 이름만 보존했다고 모든 독자의 기기에 같은 모양이 보장되지는 않는다. [CSS 글꼴 선택 규칙](https://www.w3.org/TR/css-fonts-4/#font-family-prop)

원본 글꼴 정보는 전달하되 글꼴 파일을 앱에 넣거나 게시글에 업로드하는 기능은 이번 범위에 포함하지 않는다. 네이버 편집기가 어떤 글꼴 정보를 유지하는지는 실제 카페에서 확인한 뒤 지원 범위에 반영한다.

## 배포 전 통과해야 할 검사

### 내용과 표 구조

- `앞 강조 뒤`처럼 일반 글자와 서식 글자가 섞여도 전체 글자가 남는다.
- 겹친 글자 서식 때문에 `가나다`가 `가나다나`로 늘어나지 않는다.
- 셀 안의 문단 구분과 줄바꿈이 유지된다.
- 세 열의 너비가 1:2:3이라면 모두 같은 `50%`로 바뀌지 않는다. 병합된 셀이 있는 표도 함께 확인한다.
- 셀 병합, 색상, 굵게, 밑줄, 좌·중·우 정렬과 특수문자가 정한 지원 범위 안에서 유지된다.
- 여러 표와 표 안의 표를 처리할 때 누락·중복된 결과를 완료로 안내하지 않는다.
- 변환 실패 또는 변환 중 다른 내용을 복사한 경우 사용자의 원본을 보호한다.
- 기존 자동 검사와 새로 추가한 검사가 모두 통과한다. 의도적으로 바꾸는 너비·글꼴 기대값과 기존 내용 보존 검사를 구분해 검토한다.

### 실제 한글과 네이버 카페

- 한글 for Mac 12.30.0(6544)에서 대표 표를 복사해 Safari와 Chrome 각각에 붙여넣는다.
- 비교할 표는 기본 표, 병합한 표, 다양한 글꼴·강조·줄바꿈이 있는 표를 우선 고른다.
- 원본, Windows 붙여넣기 결과, Mac 앱을 거친 결과를 같은 항목으로 비교한다.
- 실제 검증 자료를 얻기 전에는 Windows와 같은 결과를 확인했다고 안내하지 않는다.
- 편집 화면과 저장 후 화면에서 결과를 확인한다. 게시물 작성·공유는 사용자가 지정한 테스트 공간과 범위에 맞춘다.

### 설치와 실행

- 배포 ZIP의 압축을 풀어 앱을 응용 프로그램 폴더로 복사해 실행할 수 있다.
- Python이나 Xcode를 설치하지 않은 환경에서 실행할 수 있다.
- 메뉴바 상태와 안내만으로 첫 변환을 마칠 수 있다.
- 알림을 허용하거나 거절한 경우 모두 결과를 알 수 있다.
- 지원한다고 안내할 macOS와 Mac 종류를 실제 실행 결과에 맞춰 확정한다.
- 선택한 배포 방식의 서명·공증 확인과 다운로드 후 설치 검사를 통과한다.

## 진행 순서

1. **현재 상태 보존과 첫 배포 기준 정리 — 완료.** 로컬 백업을 만들었고 사용자 환경과 원본 글꼴 요구를 기록했다. 글자 크기·테두리의 구체적인 보존 규칙과 Windows 비교 자료는 후속 검증 항목으로 남겼다.
2. **변환 기능 보완 — 핵심 구현·Chrome 검사 완료, 호환성 검증 계속.** 문서 전체·여러 표·중첩 표, 정렬·배경·취소선·기본 글자 크기를 보완했다. 회귀 검사 37개와 제공 문서의 Chrome 실제 붙여넣기를 통과했다. 그림과 대각선 등 제한은 남아 있다.
3. **처음 사용하는 사람을 위한 안내 — 완료.** 사용법 영상, 메뉴바 상태 설명, 앱 정보 창과 정식 앱 아이콘을 제공한다.
4. **실사용 비교 — 제공 문서 전체의 Chrome 검사 완료.** 바깥 표 10개를 검사했고 첫 두 표는 Windows 기준 게시글과 글자·병합을 비교했다. Safari, 블로그, 저장 후 표시와 나머지 표의 Windows 기준 비교는 남아 있다.
5. **배포 인증 — 첫 배포 앱 검증 완료.** Universal 앱의 Developer ID 서명, hardened runtime, Apple 공증·티켓 스테이플과 Gatekeeper 검증을 통과했다. 첫 배포는 ZIP을 사용한다.
6. **공개 다운로드 검사 — 완료.** ZIP과 체크섬의 비로그인 HTTP 200 응답과 원본 일치를 확인했다. 다른 Mac·구형 macOS 실행은 사용자 선택으로 이번 배포 검증에서 제외했으며, 첫 배포에는 이전 공증 버전이 없으므로 실제 버전 교체는 다음 업데이트 때 검사한다.
7. **GitHub 첫 정식 배포 — 완료.** 2.0.0(빌드 1)의 ZIP과 한국어 릴리스 안내를 게시한 뒤 운영용 업데이트 안내 파일도 공개했다. 실제 Sparkle이 운영 안내를 읽고 현재 버전을 최신으로 판정하는 것을 확인했다.

단축키와 Sparkle 업데이트 확인을 구현했다. 자동 다운로드·자동 설치는 제공하지 않으며 사용자가 설치를 선택해야 진행한다. 로그인 시 자동 실행과 GitHub Actions 배포 자동화는 이번 범위에 포함하지 않는다.

## 2026년 10월 22일 유지보수와 Chrome 시험

사용자가 복사해 준 한글 표의 HTML을 로컬 진단 폴더에 보관하고, 같은 입력을 기존 Python 코드와 Swift 변환기에 넣었다. 사용자 표의 실제 내용은 Git에 포함하지 않는다. 한글 앱에서의 표 선택은 사용자가 수행했고, 이후 데이터 분석과 변환 및 Chrome 시험은 자동화했다.

기존 작성 중인 카페 탭은 보존하고 별도의 새 글쓰기 탭에서 시험했다. 글 등록 버튼과 임시저장 버튼은 누르지 않았다.

- 기존 Python과 수정 전 Swift 출력을 각각 Chrome의 실제 붙여넣기 명령으로 입력했다. 둘 다 14행·50셀, 너비 800px·높이 3,203px였다. 첫 행 칸 너비가 약 377px에서 21px까지 벌어졌다.
- 첫 개선안도 실제 클립보드 붙여넣기로 시험했다. 열 비율과 나눔바른고딕이 유지됐지만, 원본의 작은 물리적 너비를 그대로 사용하면 네이버의 최소 글자 크기와 셀 여백 때문에 높이가 여전히 약 1,542px였다.
- 두 번째 개선안은 원본 열 너비의 비율을 유지하며 본문 너비에 맞추고, 원본 줄 간격을 전달한다. 사용자의 시스템 클립보드를 보존하기 위해 이 안은 새 빈 시험 탭의 실제 네이버 붙여넣기 처리기에 표 데이터를 전달하는 보조 시험으로 확인했다. 이 시험은 네이버 모델에 표를 생성하며, 표 HTML을 화면에 직접 삽입하는 방식이 아니다. 실제 클립보드 명령과 구분해 기록한다.
- 두 번째 개선안의 표는 800px·약 727px였고 첫 행 너비는 약 95·120·112·120·112·120·120px였다. 14행·50셀의 병합 값이 원본과 같았고, 공백·표시용 줄바꿈을 제외한 각 셀의 글자가 모두 일치했다.

## 2026년 10월 24일 전체 문서와 모든 표 검사

### 수정 방향의 보조 검증

앱 소스를 바꾸지 않고 시험용 출력만 수정해, 안쪽 일정표·시간표·공간 배치도 세 개를 새 빈 편집기에서 확인했다. 이 단계는 시스템 클립보드를 사용하지 않고 네이버의 실제 붙여넣기 처리기에 데이터를 전달한 보조 시험이다.

- 문단에 `text-align`을 명시하면 왼쪽·가운데·오른쪽 정렬은 유지됐다.
- 시간표 첫 셀의 배경색을 별도로 명시하면 원래 연두색이 유지됐다. 한글 클립보드에서는 배경색이 대각선 선언과 함께 들어 있어, 현재 대각선 제거 과정에서 함께 삭제된다.
- 양쪽 정렬은 이 방식으로도 왼쪽 정렬로 바뀌었다. 별도의 호환성 확인이 필요하다.

- 중첩 표는 바깥 표의 행으로 펼친다. 안쪽 표 앞뒤의 글을 별도 칸으로 나누고 주변 셀의 행·열 병합을 조정해 내용 중복을 막는다. 지나치게 복잡한 구조는 부분 결과를 쓰지 않고 원본 클립보드를 유지하며 실패를 안내한다.
- 문단 정렬을 명시해 왼쪽·가운데·오른쪽 정렬을 전달한다. 한글이 대각선 선언 안에 붙여 보낸 배경색도 복원한다.
- HTML 주석으로 감싼 첫 스타일 규칙을 읽도록 고쳤다. 이전에는 `p.0`의 기본 10pt 크기를 놓쳐 네이버의 기본 15px로 표시됐다. 수정 후 첫 표는 Windows 기준처럼 주로 13px, 일부 11px로 표시된다.
- 취소선·기울임을 전달한다. Chrome 보조 시험에서 네이버는 `<s>`와 CSS만으로 표현한 취소선을 무시하고 `<strike>`와 `<del>`은 받아들이는 것을 확인했다. 출력은 `<strike>`를 사용하며 최종 실제 붙여넣기에서도 선이 유지됐다.
- 웹 주소가 있는 그림은 전달한다. 로컬 파일·데이터 형식 그림은 네이버에서 자동으로 받아들이지 않아 변환 완료 안내에 별도로 추가할 개수를 표시한다. 사용자가 기준 게시글의 그림이 수동 추가였는지 기억하지 못하므로, 그 그림의 유입 경로는 미확인으로 남긴다.

### 제공 문서 전체의 실제 붙여넣기

앱과 같은 최신 클립보드 모듈로 저장된 한글 입력을 변환한 뒤, 새 빈 Chrome 카페 글쓰기 탭에서 **실제 클립보드 붙여넣기 명령**으로 시험했다. 입력 직전·붙여넣기 직전에 클립보드 변경 여부를 확인했다. 기존 작성 중인 글과 원본 HWP는 변경하지 않았고 글 등록·임시저장은 하지 않았다.

## 2026년 10월 24일 형광펜 보완

사용자가 [추가 Windows 게시글](https://cafe.naver.com/f-e/cafes/31729518/articles/236?boardtype=L&menuid=5&referrerAllArticles=false)의 형광펜 재현을 지적해 재검사했다. 앞선 서식 검사에는 글자 뒤의 형광펜 색상이 빠져 있었다. 한글 클립보드에는 해당 정보가 있었지만 변환기가 글자 색상만 출력하고 글자 배경색은 출력하지 않는 것이 원인이었다.

글자와 그 상위 인라인 요소의 `background`·`background-color`를 읽어 글자 배경색으로 전달하도록 보완했다. 셀·문단의 배경색은 글자 형광펜으로 복사하지 않는다. 중첩된 굵게·밑줄 등과 함께 보존하고, 형광펜 구간 다음의 일반 글자로 색상이 번지지 않도록 검사했다.

새 빈 Chrome 편집기에서 최신 변환 결과를 네이버의 붙여넣기 처리기에 전달했다. 시스템 클립보드는 이전 시험 이후 바뀌어 있었으므로 내용을 읽거나 덮어쓰지 않았다. 이번 검증은 시스템 클립보드 붙여넣기 명령과 구분되는 **보조 붙여넣기 시험**이다.

- 문서 전체에서 형광펜이 지정된 **327글자**가 원래 색으로 유지됐다. 노랑 40글자, 연한 베이지 66글자, 연한 주황 193글자, 약간 다른 노랑 28글자다. 수치는 공백·화면 표시용 문자를 제외했다.
- 첫 표의 실제 형광펜은 **275글자**다. 노랑 16글자, 베이지 66글자, 주황 193글자가 유지됐다.
- 앞서 받은 Windows 기준 게시글의 첫 표와 비교해 **4,764글자 모두 글자와 인라인 배경색이 일치**했다. 비교에는 형광펜뿐 아니라 회색 셀 안 글자의 회색 배경 표현도 포함한다.
- 네이버는 색이 있는 셀의 배경을 같은 색의 글자 배경으로도 표현한다. 원본에 형광펜이 없는 글자는 배경이 없거나 해당 셀과 같은 색인 것을 확인했다. 이는 이번 출력에서 형광펜을 셀 전체로 확대한 결과와 구분한다.
- 바깥 표 10개, 각 칸의 글자·가로/세로 병합, 본문 너비 800px, 가로 넘침 없음과 취소선 6글자도 유지됐다.

## 2026년 10월 25일 변환 단축키

사용자가 선택한 **⌘⌥⇧P**(Command + Option + Shift + P)로 기존 **표 변환하기** 기능을 실행하도록 구현했다. 앱을 실행해 둔 동안 다른 앱을 사용 중에도 동작하는 전역 단축키다. 한글의 선택·복사나 브라우저 붙여넣기를 자동 조작하지 않으며, 사용 흐름은 **⌘C → ⌘⌥⇧P → ⌘V**다.

- macOS의 `RegisterEventHotKey`를 사용해 지정한 조합만 등록한다. 일반 키 입력 감시나 다른 앱에 키 입력 보내기를 사용하지 않으므로 별도의 손쉬운 사용·입력 모니터링 권한을 요청하지 않는다. 한글 입력 상태에서도 같은 물리 글쇠로 동작하도록 키 코드를 사용한다.
- 메뉴에 단축키를 표시하고 **단축키 설정…**을 추가했다. 조합·영문 글쇠 변경, 해제, 기본값 복원을 지원하며 저장한 설정을 다음 실행에 읽는다.
- 새 조합 등록에 실패하면 이전 단축키와 저장한 설정을 유지한다. 같은 전역 단축키를 다른 프로세스가 선점한 경우 등록 실패를 안내한다. 다른 앱 내부 단축키와 모든 사용자 지정 시스템 단축키까지 자동으로 확인한다는 뜻은 아니다.
- 키를 길게 눌러도 누른 뒤 놓는 한 동작에 한 번만 실행한다. 이미 변환된 클립보드에는 다시 쓰지 않고 붙여넣기 준비 상태를 알린다. 기존 메뉴 버튼도 같은 변환 동작을 사용한다.
- 기존 macOS 알림 권한이 있으면 시스템 알림을 사용한다. 그 외에는 메뉴바 아래의 비활성화 패널로 8초 동안 안내해 작업 창을 빼앗지 않는다. 새 알림 권한 요청이나 확인 버튼이 필요한 완료 대화상자는 띄우지 않는다.

변환 검사 30개, 기존 클립보드 검사 9개, 새 단축키 검사 6개, 합계 **45개가 통과**했다. 새 검사에서는 실제 Carbon 이벤트 전달을 거쳐 별도 시험 클립보드를 변환했고, 반복 입력 방지·설정 저장/복원·손상 설정의 기본값 처리·등록 충돌 시 이전 조합 유지·해제 후 재등록을 확인했다.

실제 앱 소스에 시험 전용 클립보드와 임시 설정을 주입한 별도 앱에서도 단축키 이벤트 → 변환 → 완료 안내를 검사했다. 변환 후 반복 입력이 클립보드를 다시 쓰지 않았고, 완료 패널 표시 후에도 원래 활성 앱이 유지됐다. 설정 창의 기본 P 조합, 사용 해제·저장, 재열기·기본값 복원을 확인했다. 사용자의 일반 클립보드와 저장된 설정은 바꾸지 않았다. 설정 화면은 컨트롤 배치와 동작을 확인했으며, 화면 제어 도구는 연결 시간 초과로 실제 앱 메뉴의 시각적 자동 검사를 마치지 못했다. 시스템이 물리 키 입력을 받아 다른 앱에서 전환 없이 전달하는 실사용 재확인은 남아 있다.

Apple Silicon·Intel Release 빌드와 로컬 서명 검증을 통과했고 최신 프로젝트 앱을 실행했다. 별도 프로세스의 등록 검사에서도 ⌘⌥⇧P가 실제로 선점돼 있는 것을 확인했다. 작업 전 파일, 검사·빌드 로그와 앱 통합 검사 결과는 Git에서 제외되는 `.build/diagnostics/shortcut-2026-10-25/`에 보관한다. 변환 엔진의 표·형광펜 처리는 이번 단축키 작업에서 변경하지 않았다.

## 2026년 10월 25일 단축키 직접 입력과 설정 창 여백

사용자가 저장 버튼 아래의 넓은 여백과 드롭다운 방식을 지적해 설정 창을 보완했다. 이전 창은 높이를 252로 고정하고 내용 아래쪽을 창 끝에서 최소 20만 떨어지게 지정해, 실제로는 66포인트 여백이 남았다.

- 사용을 끄면 **표 변환하기**와 입력칸을 시스템 비활성화 색상으로 표시한다. 메뉴에서 변환하는 기능은 유지한다.

- 시스템 버튼·체크박스·구분선·의미 기반 색상을 사용하고 최소 지원 OS인 macOS 12를 유지했다. 새 패키지는 추가하지 않았다.

## 2026년 10월 28일 피드백 및 지원 구현

메뉴바와 앱 정보 창에 같은 **피드백 및 지원** 메뉴를 추가했다. **이메일로 문의…**는 기본 메일 앱에 수신 주소·제목·편집할 본문과 실제 앱·macOS 버전을 전달한다. **GitHub에 의견 남기기…**는 문제 신고·개선 제안·사용 문의를 하나로 합친 한국어 Issue Form을 연다. **문의 이메일 주소 복사**는 웹메일 이용자도 사용할 수 있다.

사용자의 명시적 복구 요청에 따라 **피드백 및 지원**에 **이메일로 문의…**, **GitHub에 의견 남기기…**, **문의 이메일 주소 복사**를 함께 제공하도록 되돌렸다. 메뉴바의 하위 메뉴와 앱 정보 창의 시스템 풀다운 버튼이 같은 동작을 공유한다. 기존 GitHub 문의 양식과 버전 자동 입력은 유지한다.

이메일은 기본 메일 앱에서 수신 주소·한국어 제목·편집할 본문·앱 및 macOS 버전이 들어간 초안만 연다. 자동 발송이나 문서·클립보드·로그 첨부는 하지 않는다. 메일 앱 열기 실패 시 수신 주소 복사·닫기를 제공하고, 사용자가 복사를 선택할 때만 클립보드를 변경한다. 수신 주소 미설정 시 이메일 항목을 삭제하지 않고 비활성화한다. 기존 개인 수신 주소를 임의로 다시 넣지 않고, 사용자가 새로 지정한 iCloud 주소를 수신 주소로 연결한다.

결과 안내·지원·단축키 설정·메뉴·사용법 AppKit 통합 검사 5종과 Apple Silicon·Intel Release 빌드가 통과했다. 실제 수신 주소를 설정한 최종 앱을 다시 빌드한 뒤, 지원 통합 검사로 주소 연결과 이메일 항목 활성화까지 확인했다. 라이트·다크·고대비 앱 정보 창의 배치를 확인했고, 로컬 서명과 ZIP 무결성·수신 주소·실행 파일 일치를 검증했다. 복구한 앱으로 기존 실행본을 정상 종료 후 재시작했다. 실제 메일 발송·수신은 시험하지 않았으며 이번 변경을 GitHub에 게시하지는 않았다. 기록은 `.build/diagnostics/email-restore-2026-10-28/`에 보관한다.

### 이메일 문의 실제 실행 확인과 GitHub 동기화

실행 중인 앱의 정보 창에서 지원 메뉴를 열어 이메일 문의·GitHub 문의·이메일 주소 복사 항목이 함께 표시되는 것을 확인했다. 이 Mac의 기본 `mailto` 처리 앱은 Google Chrome이었으며, 실제 앱에서 이메일 문의를 실행하자 Chrome의 메일 작성 화면에 지정한 수신 주소, 한국어 제목·본문, 앱 버전 `2.0 (1)`과 macOS 버전 `27.0`이 정상 입력됐다. 문의 초안의 연결과 입력값을 실제 화면으로 확인한 결과이며, 발송이나 수신 성공을 뜻하지 않는다.

수신 확인용 시험 메일 초안을 준비한 뒤 사용자가 발송하지 않고 초안을 유지하도록 선택했으므로, 시험 메일은 보내지 않았다. 실제 수신 여부는 미확인으로 남긴다. 복구한 앱 코드·수신 주소 설정·통합 검사·README·작업 기록, 총 7개 파일만 GitHub 기본 브랜치에 동기화한다. 빌드 결과물·개인 설정·메일 화면과 초안 내용은 게시 대상에 포함하지 않으며, 정식 앱 릴리스는 별도로 진행한다.


## 2026년 10월 29일 업데이트 확인과 설정 통합

사용자의 착수 지시에 따라 **업데이트 확인…**을 **표로롱에 관하여** 바로 위에 추가하고, 기존 **단축키 설정…**을 **설정…**으로 바꿨다. 설정 창은 단축키·업데이트 영역을 함께 제공하며, **자동으로 업데이트 확인**은 기본 켬이다. 저장한 선택을 유지하고 취소·창 닫기는 변경을 버린다. 업데이트 설정만 바꾸면 단축키를 다시 등록하지 않는다. ⌘,는 같은 설정 창을 연다.

Sparkle 2.10.1을 앱 타깃에 연결했다. 수동 확인은 자동 확인을 꺼도 가능하며 자동 확인은 앱 실행 중 하루 간격이다. 자동 다운로드·자동 설치와 해당 선택지는 비활성화했다. 자동 발견은 메뉴에 **새 버전 있음**으로 알리고 다른 앱의 입력 위치를 빼앗지 않는다. 설치는 사용자가 선택한 경우에만 진행하고 변환 중 업데이트를 위한 재실행은 완료 뒤로 미룬다.

업데이트 검증용 개인 키는 로그인 Keychain의 `com.phronesis.pyororong` 계정에 보관하고 공개 키만 앱 설정에 넣었다. 개인 키는 내보내거나 소스·로그에 기록하지 않았다. 앱은 공식 저장소의 `updates/appcast.xml`을 운영 주소로 사용하도록 구성했다. 실제 공개 릴리스와 운영 안내 파일은 아직 게시하지 않았으며, 존재하지 않는 배포 파일을 가리키는 가상 안내도 만들지 않았다.

검증 결과:

- 패키지 검사 **96개**(코어 47개·Mac 모듈 49개) 통과.
- 결과 안내·설정·메뉴·업데이트·사용법 AppKit 통합 검사 **5종** 통과.
- 실제 Sparkle과 고유 시험 번들·로컬 서버로 최신/새 버전, 미지원 macOS, 시험판 제외, 404, 잘못된 XML과 수동 확인 가능 상태를 확인했다. 자동 확인 선택 저장, 기존 자동 설치 선택값 무시, 사용자 선택 전 설치 파일을 내려받지 않음과 변환 중 설치 연기도 검사했다. 일반 클립보드와 운영 사용자 설정은 검사에서 변경하지 않았다.
- 설정의 밝은·어두운·고대비 배치와 키보드 탐색을 확인했다. 메뉴의 연속 가상 클릭은 AppKit 처리 정리를 위해 클릭 사이에 60ms를 두고, 포커스 이탈 검사는 먼저 시험 창의 포커스를 확립하도록 했다. 검사 실패를 재시도하거나 검증 조건을 완화하지 않았다.
- Apple Silicon·Intel Universal 로컬 빌드와 앱·Sparkle 프레임워크·헬퍼의 ad-hoc 서명 검증 통과. 로컬 빌드 스크립트에서만 hardened runtime을 끄며 배포용 프로젝트 설정은 유지한다.
- 전체 통합검사 중 기존 지원/앱 정보 검사는 밝은 모드 아이콘 그림자 방향에서 실패했다. 기존 `AboutIconButton`의 오프셋 +2가 그림자를 위로 만드는 것을 별도 진단으로 확인했으며, 이번 업데이트 작업에서는 기존 아이콘 소스와 해당 검사를 수정하지 않았다.

배포 준비 스크립트 `scripts/prepare-update.sh`와 [업데이트 배포 안내](updates.md)를 추가했다. 스크립트는 서명·공증·버전·공개 키를 검사한 뒤 ZIP과 설치 파일 전자서명이 포함된 안내를 만들며 게시하지 않는다. ad-hoc 앱과 잘못된 메타데이터 거부 검사는 통과했다. Developer ID 인증서가 없어 정식 공증 앱 생성·공개 배포·실제 버전 교체는 아직 검증하지 못했다. 운영 안내가 공개되기 전 수동 확인의 연결 실패는 최신 버전으로 안내하지 않는다.

로그와 화면 검증 자료는 `.build/update-swift-test.log`, `.build/update-app-tests.log`, `.build/update-remaining-tests.log`, `.build/diagnostics/updates/` 및 설정·메뉴 검사 진단 폴더에 보관한다.

## 2026년 10월 29일 최종 전체 검사와 소스 저장

여러 대화에서 쌓인 현재 변경사항 전체를 보존하면서 코드·정식 에셋·라이선스·문서와 연결 관계를 검토했다. 앱 표시 이름은 **표로롱**, 프로젝트·앱 모듈·실행 파일은 `Pyororong`, Bundle ID는 `com.phronesis.pyororong`이다. 앱 아이콘·정보창·로컬 사용법 영상·통합 설정·Sparkle 업데이트 확인과 메뉴바 60Hz 갱신 및 약 0.16초 마무리를 함께 확인했다.

지원 메뉴는 **이메일로 문의…**, **GitHub에 의견 남기기…** 두 항목이며, 메뉴 안의 이메일 주소 복사와 구분선은 제거했다. 메일 앱 열기 실패 시의 주소 복사·닫기 복구 안내는 유지했다. 실제 이메일 발송과 GitHub 문의 제출은 하지 않았다.

이번 최종 상태에서 패키지 검사 **98개**(코어 47개·Mac 모듈 51개), 결과 안내·지원/앱 정보·설정·메뉴·업데이트·사용법의 AppKit 통합 검사 **6개**, Apple Silicon·Intel Universal Release 빌드와 로컬 ad-hoc 서명 검증이 모두 통과했다. 앞 절에 기록된 과거 지원/앱 정보 실패를 이번 성공으로 대체하지 않고 이력을 보존한다. 로컬 앱을 배포 준비 스크립트에 넣으면 산출물 생성 전에 거부되는 것도 확인했다.

README의 이전 완료 대기 설명과 영상·검사 설명을 갱신하고, 검사 자료 경로는 과거 날짜에 고정되지 않도록 실행별 폴더로 바꿨다. 편집용 `output/`과 `.build/`는 Git에서 제외하며 삭제하지 않는다. 정식 아이콘 원본·라이트/다크 이미지·영상·검사 코드와 선별된 검사 자료는 소스와 함께 저장한다.

실제 명령 결과·대표 화면·소스 해시와 미확인 항목은 [최종 검사 기록](validation/2026-10-29/README.md)에 보관한다. 실제 한글·네이버 붙여넣기, 다른 Mac·구형 macOS, VoiceOver·지속 60fps 실측, 운영 업데이트 UI·실제 앱 교체는 이번 검사에 포함하지 않았다. 정식 Release 발행과 배포용 서명·공증은 후속 작업이다.

## 2026년 10월 29일 첫 정식 배포

사용자가 실제 한글·네이버 붙여넣기를 이미 완료했다고 확인하고 **2.0.0(빌드 1)**의 첫 GitHub Release 게시를 승인했다. 위 최종 소스 검사에서 수행하지 않은 실제 붙여넣기 항목은 사용자 확인으로 구분해 기록한다.

배포용 앱은 Apple Silicon·Intel Universal 구조, Developer ID Application 서명, hardened runtime, Apple 공증과 스테이플된 티켓, Gatekeeper 검증을 통과했다. 로컬 개발 빌드 스크립트는 Xcode 설정에 따라 개발용 또는 ad-hoc 서명을 사용하고 hardened runtime을 끄므로, 이 앱과 배포용 앱을 구분한다.

**2.0.0(빌드 1)**의 [GitHub Release](https://github.com/largeq/nanoome-pyororong/releases/tag/v2.0.0)에 `Pyororong-2.0.0-1.zip`과 `SHA256SUMS`를 게시했다. 로그인하지 않은 다운로드에서 두 파일의 HTTP 200 응답과 원본 일치를 확인했다. 이어 기본 브랜치 `main`에 운영용 `updates/appcast.xml`을 게시했고, 공개 응답과 생성본의 바이트 일치를 확인했다.

실제 앱의 `UpdateController`와 Sparkle로 운영 안내를 확인했을 때 2.0.0(빌드 1)은 최신 버전으로 판정됐다. 일반 클립보드가 보존되고 시험용 설정이 정리된 것도 확인했다. 배포 파일 해시와 공개 다운로드·운영 안내 확인 자료는 [배포 검증 기록](validation/release-2.0.0/README.md)에 있다. 사용자용 안내는 [2.0 릴리스 안내](releases/2.0.0.md), 이후 배포 절차는 [업데이트 배포 안내](updates.md)에 둔다.

다른 Mac·구형 macOS 실행, VoiceOver 실제 음성 읽기와 지속 60fps 실측은 사용자 선택으로 이번 배포 검증에서 제외했다. 첫 배포에는 이전 공증 버전이 없으므로 실제 업데이트 다운로드·교체·재실행은 다음 업데이트 때 확인한다.
